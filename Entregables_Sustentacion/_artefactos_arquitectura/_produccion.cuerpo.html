Pruebas y cobertura

Una prueba ejecuta un pedazo del código y comprueba el resultado. La cobertura mide qué líneas y qué ramas (cada lado de un if) ejecutaron las pruebas. Un 94,2 % no quiere decir «sin errores»: quiere decir que el 94,2 % del código corrió al menos una vez en una prueba.

Cómo corren

  • pytest, pytest-django y pytest-cov (coverage.py).
  • El back crea una base PostgreSQL de prueba en cada corrida y la borra al final. Así también se prueban las funciones, el procedimiento y los triggers.
  • El front se prueba sin API: mock.patch sobre las funciones de cliente_api y se revisa el HTML.

El reporte

El CI corre pytest --cov --cov-fail-under=70: si la cobertura baja del 70 %, se pone rojo. Cada ejecución sube htmlcov/ como artefacto cobertura-backend.

Integración continua

Con cada push y cada PR a main, desarrollo y pruebas, GitHub Actions instala el proyecto en un Ubuntu limpio y corre las pruebas. Estos son los pasos del back, en orden.

  1. permissions: contents: read

    El token del flujo solo puede leer el repositorio: no escribe, no comenta, no publica.

  2. Servicio postgres:18

    Levanta un PostgreSQL de verdad, con un chequeo de salud (pg_isready) antes de seguir.

  3. actions/checkout@v6 y setup-python@v6

    Trae el código y pone Python 3.14. Las versiones v6 corren en Node 24.

  4. Check dependency lock

    bloquear_dependencias.py --check falla si requirements.lock no corresponde a requirements.txt.

  5. Install dependencies

    pip install --require-hashes --only-binary :all: -r requirements.lock: solo wheels cuyo SHA-256 está en el lock.

  6. Check migrations

    makemigrations --check --dry-run falla si alguien cambió un modelo y olvidó la migración.

  7. Run tests with coverage

    pytest -q --cov … --cov-fail-under=70: las 854 pruebas, con el mínimo de 70 %.

  8. Upload coverage report

    Con if: always(), sube htmlcov/ aunque fallen las pruebas.

El del front tiene el lock, la instalación y pytest -q, sin PostgreSQL ni migraciones.

--require-hashes

pip compara el SHA-256 de cada archivo con el del lock. Si alguien cambia un paquete en PyPI, el hash no coincide y no se instala. El == de requirements.txt fija la versión, pero no garantiza que el archivo sea el mismo.

--only-binary :all:

Solo instala wheels, paquetes ya construidos. Así nunca ejecuta el setup.py de un paquete, que es un programa y puede correr cualquier código al instalarse.

Oracle Cloud · systemd · /etc/admind/py/

El servidor

Una máquina virtual de Oracle Cloud con Ubuntu 24.04, 2 vCPU y ~1 GB de RAM. Front, API y base viven en ella. En el servidor corren PostgreSQL 16 y Python 3.12; en local y en el CI, 18 y 3.14.

gunicorn y systemd

gunicorn es el servidor de aplicaciones de producción para Django; runserver es solo para desarrollar. systemd es el gestor de servicios de Linux: arranca cada servicio con la máquina y lo reinicia si falla.

Cloudflare Tunnel

cloudflared abre desde el VPS una conexión saliente y cifrada hasta Cloudflare, y las peticiones a admind.detkor.com entran por ahí. No hace falta abrir el 80 ni el 443, y el certificado HTTPS lo pone Cloudflare en el borde.

Configuración de producción

Cada servicio usa un módulo de settings en /etc/admind/py/ que importa el del repositorio y lo sobrescribe. Las claves (base, correo, SECRET_KEY, CORS_ALLOWED_ORIGINS) están en el .env del servidor; los repos solo traen .env _ejemplo.

Despliegue continuo

  1. Merge a main

    GitHub manda un webhook a deploy-admind.detkor.com, que entra por el mismo túnel.

  2. server.py valida la firma HMAC SHA-256

    GitHub firma el cuerpo con un secreto que solo conocen GitHub y el servidor. El servidor recalcula la firma; si no coincide, descarta la petición. Sin eso, cualquiera que conociera la URL podría disparar despliegues.

  3. Filtra y encola

    Solo acepta push a refs/heads/main de los dos repos, descarta entregas repetidas, valida el commit y deja un trabajo en la cola (64 como máximo). Corre con un usuario dedicado y el aislamiento de systemd.

  4. Una unidad .path ve el trabajo

    systemd vigila la carpeta de la cola y lanza deploy_queue.py, que corre el script del proyecto.

  5. El script despliega y reinicia

    Back y front hacen pull, instalan y reinician su servicio; el back además migra la base y el front recoge los estáticos.

Repaso

Responde en voz alta antes de abrir cada una.

¿Qué mide la cobertura y qué no?
Qué líneas y ramas se ejecutaron en las pruebas. No garantiza que el resultado sea correcto en todos los casos.
¿Por qué las pruebas corren contra PostgreSQL y no SQLite?
Porque las reglas clave las impone PostgreSQL: FK compuestas, índices únicos parciales y triggers. En SQLite no existirían.
¿Qué pasa si alguien cambia un modelo y olvida la migración?
El paso Check migrations falla y el CI se pone rojo.
¿Qué hacen --require-hashes y --only-binary :all:?
El primero rechaza cualquier paquete cuyo SHA-256 no esté en el lock. El segundo instala solo wheels, así que nunca ejecuta un setup.py.
¿Por qué la calificación de seguridad sigue en C?
La fija la peor vulnerabilidad abierta y queda una MAJOR en cada repo. Las incidencias bajaron de 20 a 16.
¿Por qué no se ve el puerto 8000 desde internet?
La API escucha solo en 127.0.0.1 y no hay puertos de entrada para la web: todo entra por el túnel hasta el front.
¿Qué valida el webhook antes de desplegar?
La firma HMAC SHA-256, que sea un push a main de uno de los dos repos y que la entrega no esté repetida.
¿Dónde viven los secretos de producción?
En el servidor: el .env y los settings de /etc/admind/py/. Los repos solo traen .env _ejemplo.
¿Qué pasa si se cae un servicio?
systemd lo reinicia. Si se cae todo el servidor, el plan B son las capturas de la presentación y del Manual de Usuario.
