El sistema completo

El navegador solo habla con el front. El front le habla a la API de servidor a servidor, dentro del mismo VPS, y solo la API toca PostgreSQL. Nada de la API está publicado en internet.

Por qué dos servidores

El objetivo del proyecto es que el back y el front estén separados y se comuniquen por una API. Otra interfaz, como una app móvil, podría usar la misma API sin tocar el backend. El front tiene DATABASES = {}: no puede tocar la base.

Por qué el navegador no llama a la API

Las pantallas se generan en el servidor del front. Así el token de sesión se queda en el servidor y el navegador solo tiene una cookie HttpOnly, que JavaScript no puede leer.

cliente_api/http.py → apps/<app>/views.py → servicios.py → models.py

El recorrido de una petición

Un residente abre la lista de sus reservas. Este es el camino completo, en orden. Es la pregunta que más amarra todo lo demás.

  1. NubeCloudflare recibe https://admind.detkor.com

    Pone el HTTPS en el borde y manda la petición por el túnel cifrado de cloudflared hasta el gunicorn del front, en 127.0.0.1:8001.

  2. FrontSesionRequeridaMiddleware revisa la sesión

    Sin sesión, manda a /ingresar/. Solo las vistas marcadas con @publica se abren sin sesión: el ingreso, recuperar la contraseña y el enlace que quita el segundo factor.

  3. FrontLa vista llama a cliente_api

    pedir() saca el token de la sesión del servidor, lo pone en Authorization: Token … y llama a la API con requests, con 10 segundos de espera máxima.

  4. APICorsMiddleware

    Solo importa si la petición viene de un navegador. Aquí la llamada es de servidor a servidor, así que no interviene; cierra la puerta si algún día la API se publica.

  5. APIAutenticacionPorToken

    Calcula el SHA-256 del token y busca un TokenDeSesion vigente con esa huella. Si no hay, responde 401.

  6. APIEl segundo factor, si el rol lo exige

    Superusuario, Administración y Secretaría tienen permisos sensibles: sin el segundo factor verificado, la API responde 403.

  7. APIVistaDeConjunto fija el conjunto activo

    Lo toma de la sesión del token, nunca de la petición. Si alguien manda conjunto en la URL o el cuerpo, responde 400. Guarda el conjunto en una ContextVar.

  8. APIexigir_permiso(request, "reserva.ver")

    Primera línea de la vista. Si el rol no tiene ese permiso, 403. El menú del front solo decide qué se ve; quien decide de verdad es la API.

  9. APISerializer y servicio

    El serializer valida la forma de la entrada (400 si falla). El servicio, en servicios.py, aplica la regla de negocio y no sabe nada de HTTP.

  10. APIEl Manager del modelo consulta

    ManagerDeConjunto agrega solo WHERE conjunto_id = activo. Nadie tiene que acordarse de filtrar.

  11. BasePostgreSQL responde

    Con sus propias defensas: FK compuestas, índices únicos parciales, CHECK y triggers. Vuelve JSON al front, que arma el HTML.

El patrón de errores

El servicio dice qué pasó: lanza FranjaOcupada. La vista decide cómo se dice por HTTP: 409 "Otra persona está tramitando esta franja". Así el servicio no sabe nada de HTTP y se puede probar llamando una función de Python.

Dónde va cada regla

  1. ¿Lo prohíbe la ley? La operación no existe.
  2. ¿Quién puede intentarla? Permiso en la vista.
  3. ¿Se ve en la petición? Serializer.
  4. ¿Necesita el estado guardado? Servicio.
  5. ¿Tiene que ser imposible aunque se salten el código? Además, restricción en la base.
Para el jurado

Si en views.py apareciera Area.objects, la vista se estaría saltando dos capas. Si en servicios.py apareciera Response, el servicio sabría de HTTP y no se podría reutilizar desde otra entrada, como una importación por Excel.

apps/comun/aislamiento/ · apps/comun/modelos_base/

Aislamiento entre conjuntos

Una sola base guarda a todos los conjuntos, distinguidos por conjunto_id. Si una consulta olvidara filtrar, la app no se rompería: le mostraría a un residente de un conjunto los datos de otro. Por eso el filtro no depende de que alguien se acuerde, y hay dos líneas de defensa.

Primera línea: el código

  • VistaDeConjunto, la clase base de toda vista con datos de un conjunto, fija el conjunto activo desde la sesión del token.
  • contexto.py lo guarda en una ContextVar: cada petición ve el suyo.
  • ManagerDeConjunto reemplaza Modelo.objects y filtra siempre. Sin conjunto activo, falla a propósito.
  • ModeloDeConjunto: id UUID, el conjunto, el Manager filtrado y un save() que rechaza escribir en otro conjunto.

Segunda línea: la base

Llaves foráneas compuestas, escritas por fk_compuesta() en las migraciones. Una fila no puede apuntar a otra de otro conjunto: la base la rechaza.

-- en esencia

  REFERENCES areas_area (id, conjunto_id)

La prueba estrella

tests/aislamiento/test_intruso.py recorre todas las rutas de la API con un usuario de otro conjunto y con uno sin permiso. Si alguien agrega una vista que no hereda de VistaDeConjunto, la prueba falla.

Por qué no es un middleware

Los middleware de Django corren antes de que DRF lea el token. Por eso el trabajo lo hace VistaDeConjunto, que corre justo después de autenticar.

Por qué no Row Level Security

Se evaluó y se descartó: exige una variable de sesión bien puesta en cada conexión. Sostener eso cuesta más que las FK compuestas, que impiden el dato cruzado donde nace.

Sesión, permisos y seguridad

  1. Ingreso con correo y contraseña

    La contraseña se compara con su hash PBKDF2-SHA256, con sal y 1.000.000 de iteraciones, el de Django. La recuperación da 3 enlaces por hora, que vencen en 1 hora.

  2. La API crea un token opaco

    secrets.token_urlsafe(32): 32 bytes aleatorios que no se pueden leer ni descifrar. La base guarda solo su huella SHA-256 en TokenDeSesion.

  3. El front lo guarda en su sesión

    Sesión en archivos del servidor, con el token, el conjunto activo, los permisos, el rol y el estado del segundo factor. El navegador solo recibe una cookie HttpOnly y Secure.

  4. Vence 1 hora después del ingreso

    Se cuenta desde el ingreso, no desde el último uso. La sesión del front vence a la misma hora.

  5. Cerrar sesión borra la fila

    El token deja de valer de verdad. Cambiar la contraseña también cierra las sesiones. Y el front manda Cache-Control: no-store: el botón Atrás no muestra nada.

Permisos en código

El catálogo vive en apps/permisos/catalogo.py: cada rol es una lista de permisos como reserva.aprobar. El administrador solo asigna roles. Un solo rol vigente por persona y conjunto: se cambia, no se suma.

Se valida en tres sitios

El front oculta lo que el rol no puede usar. La API exige el permiso en cada endpoint (403). Y los datos de cada conjunto están aislados (404).

CORS Hecho

django-cors-headers con lista blanca desde CORS_ALLOWED_ORIGINS: en la nube, solo https://admind.detkor.com. Sin comodín ni credenciales. Cierra la puerta de atrás si la API se publicara.

JWT No implementado

Se decidió un híbrido (JWT firmado más la tabla para revocar) y no alcanzó el tiempo. El token opaco se revoca al instante; un JWT puro vale hasta que vence y para revocarlo hace falta una tabla como esta.

Frontend/Admind_Front-End · cliente_api/ · apps/ · templates/ · design-system/

El front por dentro

Django con plantillas: el HTML se arma en el servidor. Alpine.js aparece solo donde hay interacción real, y el estilo sale de un sistema de diseño propio.

cliente_api/: el mesero

Un archivo por app de la API, una función por endpoint. Todas usan http.py → pedir(request, metodo, ruta, datos):

  • pone el token de la sesión en la cabecera;
  • llama con requests, 10 s como máximo;
  • si la API no responde, ApiNoDisponible;
  • si responde con error, ErrorDeApi, con el mensaje en español y los errores por campo.

La sesión y los errores

  • sesion.py: abrir_sesion() guarda token, conjunto, permisos y rol; tiene_permiso() decide qué se ve.
  • SesionRequeridaMiddleware: toda pantalla exige sesión salvo las @publica.
  • ErroresDeApiMiddleware: API caída → 503; 401 → al ingreso; 403 y 404 → su página propia.

Diseño

Tokens de color y tipografía y componentes am-*, sin Bootstrap ni Tailwind. Verde #0E6B5A, Archivo e Inter. Cada conjunto elige su acento (8 o uno propio) y su foto 1:1.

Dónde hay Alpine.js

La solicitud de reserva con su cuenta regresiva de 3 minutos, el color y la foto del conjunto, el paso de viviendas del asistente, los buscadores de Unidades y Usuarios y el detalle de la vivienda. La cuenta regresiva solo muestra: el vencimiento lo decide la API.

¿Por qué no React?

La app es sobre todo formularios y tablas. Con plantillas no hay npm ni compilación, y el token se queda en el servidor; con React tendría que vivir en el navegador.

El bloqueo de franjas

Si 50 residentes pulsan «Reservar» a la vez, solo uno obtiene la franja. tomar() intenta el INSERT en una transacción sin preguntar antes si está libre; si el índice único parcial lo rechaza, lanza RecursoOcupado. La base decide, una sola vez.

Los archivos

comprobantes.py valida cada archivo por su firma (PDF, JPG o PNG, hasta 5 MB), no por el nombre ni por lo que dice el navegador, y calcula su SHA-256. Se guardan dentro de la base.

PostgreSQL · admind_db · migraciones con RunSQL

La base de datos

42 tablas en PostgreSQL. La base impone reglas por sí misma, para que valgan aunque alguien entre por SQL directo, por el shell o por un script que se salte el código.

Índice único parcial

No puede haber dos solicitudes bloqueantes sobre la misma franja:

-- en esencia
UNIQUE (area, fecha, hora_inicio)
WHERE estado IN ('EN_SOLICITUD',
  'APARTADA', 'RESERVADA')

Sin borrado físico

Se cierra una vigencia o se anula con motivo. Ninguna FK con ON DELETE CASCADE. Las tablas clave tienen un trigger que impide el DELETE.

Función o procedimiento

Una función devuelve datos y se usa dentro de un SELECT. Un procedimiento no devuelve nada, se llama con CALL y sirve para hacer algo: expirar bloqueos es una acción; las otras cuatro son consultas.

5 triggers, 2 reglas distintas

trg_sin_borrado_fisico protege casos, infracciones, pagos y reservas. trg_infraccion_anulada_inmutable impide modificar una infracción anulada. Todos son BEFORE y lanzan RAISE EXCEPTION.

Frente al MER inicial

El MER suponía varios roles por persona y un rol Consejo: quedó un rol vigente por conjunto y 5 roles. El estado de la reserva vive en la solicitud, no en la franja, que es solo una coordenada. Y aparecieron tablas que el MER no tenía: la auditoría, los tokens de sesión y las del segundo factor.

Para estudiar

Repaso

Responde en voz alta antes de abrir cada una.

¿Por qué hay dos servidores Django y no uno?
Porque el proyecto exige back y front separados que se hablen por una API. Otra interfaz podría usar la misma API. El front ni siquiera tiene base de datos configurada.
¿Qué hace la vista y qué no hace?
Exige el permiso, valida con el serializer, llama al servicio y traduce las excepciones a HTTP. No consulta el ORM para decidir ni contiene reglas de negocio.
¿Dónde se filtra por conjunto?
En ManagerDeConjunto, con el conjunto que VistaDeConjunto fija en una ContextVar. Las FK compuestas lo respaldan en la base.
¿Qué pasa si alguien manda conjunto en la petición?
La API responde 400. El conjunto solo sale de la sesión del token.
¿Por qué 404 y no 403 para lo de otro conjunto?
Un 403 confirma que el recurso existe, y esa confirmación ya es información filtrada.
¿Qué guarda la base del token de sesión?
Solo su huella SHA-256. Cerrar sesión borra la fila y el token deja de valer.
¿Cómo se evita que dos personas tomen la misma franja?
Con un índice único parcial y un INSERT dentro de una transacción, sin preguntar antes si está libre. Si el índice lo rechaza, RecursoOcupado.
¿Por qué cuatro funciones y un procedimiento?
Las funciones devuelven datos para leer. El procedimiento hace un UPDATE y no devuelve nada, por eso se llama con CALL.
¿Por qué el correo sale con on_commit y en un hilo?
Para que solo salga si la operación quedó guardada, y para que un SMTP lento no haga pasar a la API de los 10 segundos que espera el front.
¿Qué pasa con una vista nueva que no hereda de VistaDeConjunto?
Falla con 500 porque no hay conjunto activo, y la prueba del intruso la marca como ruta no registrada.
